Prompt, retrieve or fine tune? A practical guide to using LLMs efficiently

Anjali Parihar, 6 October 2026

A question I keep seeing in AI discussions is some version of this: "Should we fine tune a model for this?" Usually the honest answer is "not yet." Fine tuning sounds like the serious, professional option, but it's often the most expensive way to solve a problem that a good prompt or a search step would have solved in an afternoon.

So I want to share how I think about it. Not every task needs the biggest model, and not every problem needs training. Efficiency comes from matching the tool to the job.

Start with the cheapest thing that could work

I think of LLM customization as a ladder. Each step up costs more time, more money, and more maintenance. You only climb when the step below genuinely isn't enough.

Step 1: Prompting. Clear instructions, a few good examples of what you want, and a defined output format. This costs nothing to change and works surprisingly often. If you haven't tried giving the model three solid examples, you're not ready to fine tune.

Step 2: Retrieval augmented generation (RAG). When the model needs knowledge it doesn't have, like your company's documents, product details, or anything that changes often, you don't teach it. You look the information up and hand it over in the prompt. Updating knowledge is as easy as updating a document.

Step 3: Parameter efficient fine tuning. Techniques like LoRA train a small set of extra weights on top of a frozen model, often only a tiny fraction of its parameters. QLoRA goes further by loading the base model in a compressed 4 bit format, which makes fine tuning possible on a single GPU. This is where you teach behavior: a style, a format, a narrow skill.

Step 4: Full fine tuning. Updating all of a model's weights. Powerful, but expensive, and rarely necessary unless you're building something truly specialized at large scale.

The one rule that saves the most money

Here's the distinction that clears up most confusion:

Use RAG to give a model knowledge. Use fine tuning to change its behavior.

Fine tuning is a poor way to teach facts. Training bakes knowledge into the weights at a fixed point in time, so when your prices, policies, or products change, the model is out of date and you have to train again. And a model fine tuned on facts can still confidently mix them up. Retrieval keeps facts outside the model, where they're easy to update and easy to check.

Fine tuning shines when the problem is how the model responds rather than what it knows. A consistent brand voice. A strict output format your systems depend on. A narrow classification task. Domain language a general model keeps getting wrong.

Matching the approach to the use case

Use caseBest starting pointWhy
Answering questions over company documentsRAGKnowledge changes, and answers should point to sources
Customer support with up to date policiesRAG plus a good promptPolicies change, tone can be set in the prompt
Writing in a consistent brand voiceLoRA fine tuningStyle is behavior, and hard to fully capture in a prompt
Extracting fields from thousands of documents dailyFine tuned small modelHigh volume makes a small, cheap model worth training
Classifying support ticketsSmall model or classical MLSimple labels rarely need a large model
Rare, complex reasoning tasksLarge model with careful promptingLow volume, so training cost isn't worth it
Exact calculations and lookupsNo LLM: rules, SQL, or codeDeterministic tasks need deterministic tools

That last row matters more than people think. Coming from a data background, I've seen how tempting it is to throw an LLM at everything. But if a SQL query or a simple rule can answer the question exactly, it will be faster, cheaper, and correct every single time. An LLM is a great tool for language and judgment. It's an expensive calculator.

Efficiency for low priority work

Not every task is urgent, and that's a huge opportunity to save money.

Route by difficulty. Send easy, routine requests to a small, fast model and only escalate hard ones to a large model. Many requests in real systems are simple, so a basic router can cut costs dramatically without users noticing any difference.

Batch what can wait. Nightly summaries, report generation, tagging old documents: none of this needs an instant answer. Many providers offer batch processing at a discount, and you can run it when systems are quiet.

Cache repeated work. If the same long instructions or documents appear in many requests, prompt caching avoids paying to process them again and again.

Distill for scale. If a large model performs a task well and you need to run it millions of times, you can use its outputs to train a smaller model. This is called knowledge distillation: the big model teaches, the small model does the daily work.

Compress for serving. Quantization stores a model's numbers in fewer bits, so it needs less memory and runs faster, usually with only a small loss in quality. It's how capable models now run on a single GPU, and sometimes on a laptop.

Before you fine tune, check your data

If you do decide to fine tune, remember that training doesn't just learn from your data, it amplifies it. During training, backpropagation adjusts the model to match your examples as closely as possible, including their mistakes. Inconsistent labels, duplicated examples, and outdated information all get learned.

I wrote about this in more detail in my post on data quality for agent memory, but the short version is: a few hundred clean, consistent, carefully reviewed examples often beat thousands of messy ones. Data quality is still the cheapest place to improve a model.

A simple decision checklist

When a new use case comes up, I ask these questions in order:

  1. Can rules, SQL, or regular code solve it exactly? Then don't use an LLM.
  2. Does a well written prompt with a few examples work? Then stop there.
  3. Does the model lack knowledge, or does that knowledge change often? Add retrieval.
  4. Is the problem the model's behavior, style, or format, even with good prompts? Consider LoRA fine tuning.
  5. Will this run at very high volume? Consider a smaller fine tuned or distilled model.
  6. Is the task low priority? Batch it, route it to a small model, or cache it.

The real meaning of efficiency

The most efficient AI system isn't the one with the most advanced technique. It's the one where every part earns its place. A prompt where a prompt is enough. Retrieval where knowledge changes. Training only where behavior truly needs to change. And plain old code wherever the answer has to be exactly right.

Choosing the simplest tool that works isn't a lack of ambition. It's what makes AI something a business can actually afford to run.
